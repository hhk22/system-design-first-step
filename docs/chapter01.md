
# 시스템 디자인 핵심 목표 4가지 

## 신뢰성

신뢰성은 시스템이 정상적으로 작동하는 능력을 의미. 시스템의 오류없이 사용자의 의도대로 정상적으로 동작하는 정도. 

### 신뢰성을 높히는 방법

- 테스트(단위 / 통합)
- API 응답/에러 일관성
- 트랜젝션으로 데이터 정합성 유지 

## 성능

시스템이 주어진 자원 내에서 사용자 요청을 빠르고 안정적으로 반응하는 특성

### 성능을 높히는 방법

- 캐싱 (ex. redis)
- 비동기 처리
- DB 최적화 

## 가용성

서비스가 중단되는 시점없이 24시간 265일 가능한 정도를 나타내는 지표. 

### 가용성을 높히는 방법

- 단일 장애 지점(SPOF)이 없어야 한다. 
- 이중화 
- 재시도 및 실패 로직 설계 
- 장애 감지 및 요청 통제 (ex. 로드 밸런서)

## 확장성

시스템이 사용량 증가에 따른 확장성이 가능한 정도. 

### 확장성을 높히는 방법

- Scale-up/Scale-out
- DB분산
- 비동기처리(ex. 메세지 큐)

# 주요 시스템 컴포넌트

## 웹서버 & 웹 애플리케이션 서버(WAS)

웹서버는

- 정적 파일 서빙
- 요청 필터링
- 로드 밸런싱

웹 애플리케이션 서버는

- 비즈니스 로직 처리가 필요한 API 요청 수행

보편적인 구조는

Client <---> 웹서버 <---> WAS 

간단하게 개발할때는 

Client <---> WAS 구조도 사용함. 

## 로드 밸런서 - 부하 분산 방식

- 라운드 로빈
    - 요청이 고르게 들어오는 상황
    - 서버들이 유사한 성능일때
- Least Connection
    - 요청시간이 길고 불균형할때
- IP Hash
    - 세션 유지가 필요할때 (ex. 로그인 상태 유지)

## API 게이트웨이

클라이언트와 백엔드 사이의 단일 진입점. 요청을 적절한 서비스로 라우팅하고 공통 기능을 중앙에서 처리. (ex. Nginx, Kong)

## 서비스 디스커버리

동적으로 변하는 서비스 인스턴스의 위치를 자동으로 찾아주는 매커니즘

### 서비스 디스커버리 - Client Side

- Client <--> Service Registry <--> 서버1, 서버2, ...
    - Client단에서 Service Registry에 조회해 서버리스트를 얻은후, Client에서 직접 해당 서버에 요청을 날리는 구조. 

### 서비스 디스커버리 - Server Side

- Client <--> API Gateway  <--> 서버1, 서버2, ...
                           <--> Service Registry
    - Client단에서 API Gateway에 요청을하면 Gateway가 Service Registry에 조회한 후, 해당 서버에 요청하는 구조. 

## DB 선택을 위한 핵심 개념

### 확장성

#### 수평확장 - Read Replica

- DB복제본을 만들어 읽기 부하를 분산
- 복제 시점 차이로 인해 데이터 일관성 문제 발생 가능

#### 수평확장 - 수직 파티셔닝

- 데이터의 칼럼을 분리해서 저장

#### 수평확장 - 수평 파티셔닝

- ex) 날짜별로 데이터를 다른 서버에 저장 가능
    - 파티션 단위로 쿼리 성능 최적화 및 오래된 데이터 삭제 가능 및 데이터 관리 용이.

#### 수평확장 - 샤딩

- 수평파티셔닝의 하위 개념
- 병렬 처리로 인한 성능 향상.
- 복잡한 샤드 키 설계는 단점, 운영 복잡성이 증가한다. 

- Hash Based
    - 데이터가 고르게 분포
    - 범위 쿼리 어려움
    - 샤드 추가시, 데이터 재분배
- Ranged Based
    - 범위 쿼리에 유리
    - 데이터 불균형 가능
- Consistent Hashing
    - 샤드 수 변경시 변경되는 데이터 최소화
    - 로직이 복잡해 디버깅이 어렵고, 라우트 테이블 관리의 어려움

### 가용성

DB가 장애 상황에서도 얼마나 계속 동작할 수 있는가

#### 복제

- Leader - Follower 구조
    - Leader: Write/Read
    - Follower: Read
    - 단순한 구조, 충돌 적음
    - Leader장애시, Failover필요, 쓰기 확장 어려움

- Leaderless 구조
    - 장애에 강함
    - 일관성이 유지하기 어려움

#### Failover

Primary 장애시, Replica중, 하나를 Primary로 승격해 서비스 지속

### 일관성

- 강한 일관성
    - 복제될때까지 읽기 차단
    - 일관성이 높지만, 응답이 느리고 낮은 가용성
- 최종적 일관성
    - 모든 노드가 최종적으로 일관성을 가짐
    - 고강용성, 쓰기 지연 없음
    - 단점: 일시적으로 오래된 데이터 가짐
